# VocaGate Care 完整会员平台设计

**日期：** 2026-07-11

**状态：** 已完成方案讨论，等待书面规格确认
**范围：** VocaGate Care 中国大陆首发及海外扩展基础

## 1. 背景

VocaGate 的核心识别、门控和按键控制能力保持开源免费。商业化不通过锁定核心功能实现，而是提供一套低价、可选的官方维护服务：自动检查应用版本、一键更新、跨端兼容检查、配置迁移和更新失败保护。

产品对外统一称为：

> VocaGate Care 官方维护计划

中国大陆价格为 `¥6/年`，其他地区价格为 `US$6/年`。价格代表官方维护服务，不代表软件本体售价。

## 2. 目标

本设计需要实现以下目标：

1. 免费用户无需登录即可长期使用完整核心功能。
2. Care 用户可以通过账号管理最多 5 台设备。
3. 中国首发支持邮箱验证码登录和支付宝支付。
4. Care 用户可以在 Android、Windows 和 macOS 上获得官方一键更新能力。
5. 更新前备份配置，更新后执行兼容性和健康检查。
6. 自动续费由用户明确选择，并可随时关闭。
7. 账号、支付或更新服务故障时，核心门控功能继续工作。
8. 更新服务、客户端和协议继续开源，允许用户配置自己的更新服务器。
9. 不上传摄像头画面、音频或人脸、嘴部识别数据。

## 3. 非目标

首发版本不包含：

- 手机号登录或短信验证码。
- 微信、Google、GitHub 登录。
- 微信支付或海外支付。
- 自动扣款强制开启。
- 云端配置同步。
- 远程控制识别功能或远程停用客户端。
- Android 静默安装或系统级自动降级。
- 依靠 DRM、代码混淆或隐藏安装包限制 Community 用户。
- Supporter、Sponsor 等多档赞助计划。
- SDK、硬件和 B 端授权管理。

这些能力保留扩展接口，但不进入 Care 中国首发范围。

## 5. Community 与 Care 边界

### 5.1 VocaGate Community

Community 永久免费，包括：

- Android、Windows、macOS 核心识别与门控功能。
- GitHub 源代码。
- GitHub Release 安装包。

### 5.2 VocaGate Care

Care 在 Community 基础上增加：

- 应用版本每日自动检查。
- 官方安装包一键下载与升级。
- 官方签名和下载加速。
- Android、Windows、macOS 版本兼容检查。
- 更新前配置快照。
- 配置格式自动迁移。
- Windows 和 macOS 更新失败回滚。

- 稳定版、测试版更新通道。
- 账号下设备管理。
- 到期和自动续费提醒。

官方安装包仍可发布到 GitHub。Care 的价值是省心、可靠和官方维护，不是对二进制的独占访问。

## 6. 总体架构

采用“模块化单体 API + 独立静态更新源”的架构。

```text
Android / Windows / macOS
            |
            | HTTPS API, device authorization, entitlement, update check
            v
     VocaGate Care API
            |
      +-----+--------------------+
      |                          |
      v                          v
 PostgreSQL               Tencent COS / CDN
 users, orders,           signed installers,
 devices, releases        manifests, profiles
      ^                          ^
      |                          |
支付宝异步回调             离线发布与签名工具

Browser
  |-- 用户中心
  |-- 邮箱登录
  |-- 支付页面
  |-- 设备管理
  `-- 管理后台
```

### 6.1 服务端技术栈

- Java 21。
- Spring Boot 3。
- Spring Security。
- PostgreSQL。
- Flyway 数据库迁移。
- Spring MVC + 服务端渲染页面。
- Caddy 提供 HTTPS 和反向代理。
- 腾讯云 COS 保存版本化安装包和模型资源。
- 腾讯云中国大陆区域作为中国生产环境目标；东京 CVM 只用于开发、测试和不含个人信息的静态更新资源。

首发不拆微服务，不引入消息队列和 Redis。定时提醒、支付对账和清理任务先使用数据库锁和 Spring 调度器完成。只有出现明确容量或隔离需求后再拆分。

### 6.2 服务端模块

Care API 内部按业务边界分为：

- `identity`：邮箱身份、验证码、浏览器会话和账号合并。
- `device`：设备注册、授权、撤销和 5 台设备限制。
- `billing`：订单、支付宝交易、退款、回调和对账。
- `membership`：Care 生效、到期、续费和取消。
- `release`：版本、更新通道、兼容关系和发布状态。
- `download`：临时下载授权和下载审计。
- `notification`：登录验证码、到期提醒和扣款提醒。
- `admin`：人工开通、用户查询、订单处理和发布管理。
- `audit`：高风险管理操作和安全事件记录。

模块在一个进程内运行，但只通过明确的服务接口和数据库边界协作，不直接共享控制器或外部 DTO。

## 7. 账号与登录

### 7.1 首发登录方式

首发只支持邮箱验证码，不设置传统密码。

腾讯云 SES 通过 API 发送验证码。按照当前公开价格，邮件按量价格为 `¥0.0019/封`，每个腾讯云账号有累计 1,000 封免费额度。独立 IP 不进入首发采购范围。

验证码规则：

- 6 位数字。
- 10 分钟失效。
- 只能成功使用一次。
- 服务端只保存带服务端密钥的哈希，不保存明文。
- 同一邮箱 60 秒内不能重复发送。
- 同一邮箱每小时最多 5 次。
- 同一邮箱每天最多发送 20 次。
- 同一 IP 每天最多触发 100 次，超过后拒绝发送并记录风险事件。
- 单个验证码最多验证 5 次，达到上限后立即失效。
- 邮箱或 IP 在 10 分钟内出现 3 次失败挑战后要求完成人机验证。
- 登录失败返回统一文案，避免泄露邮箱是否已注册。

### 7.2 原生客户端授权

Android、Windows 和 macOS 不嵌入账号密码表单，采用类似 OAuth Device Authorization 的浏览器授权流程：

1. 客户端生成随机安装 ID。
2. 客户端请求一次性 `device_code` 和用户可输入的 `user_code`。
3. 客户端打开系统浏览器，并显示 `user_code` 作为备用。
4. 用户在浏览器中完成邮箱验证码登录。
5. 页面显示设备名称和平台，用户确认授权。
6. 客户端每 3 秒轮询一次授权状态，并在批准后取得设备级刷新令牌。
7. 后续客户端使用短期访问令牌访问 Care API。

`device_code` 是仅客户端持有的 256 位随机密钥，不显示给用户；`user_code` 是 8 位易输入短码，只能用于浏览器确认。授权记录 10 分钟失效，状态只能按 `PENDING -> APPROVED/DENIED/EXPIRED -> CONSUMED` 转换。刷新令牌在客户端成功领取后，授权记录立即进入 `CONSUMED`，不能重复领取。

首发不实现设备密钥证明或硬件绑定。设备软限制依赖随机安装 ID、刷新令牌和用户自助撤销，避免为低价维护计划引入三端密码学适配。后续出现明确令牌窃取风险后，再单独设计设备公钥证明。

### 7.3 凭据保存

- Android：Android Keystore。
- Windows：Windows Credential Manager 或 DPAPI。
- macOS：Keychain。
- 服务端：刷新令牌只保存不可逆哈希、过期时间和撤销状态。

访问令牌有效期为 15 分钟，刷新令牌有效期为 90 天。每次刷新都轮换刷新令牌；旧令牌再次出现时，撤销该设备的整个令牌族并要求重新登录。

### 7.4 后续身份提供商

`user_identities` 支持 `EMAIL`、`WECHAT`、`GOOGLE` 和 `GITHUB`。首发只启用 `EMAIL`。

后续增加第三方登录时，已登录用户必须主动绑定。若第三方返回已验证邮箱，可以提示与现有账号合并，但不能仅凭相同字符串邮箱自动合并两个账号。

## 8. 设备管理

每个 Care 账号最多保留 5 台活跃设备。Android、Windows 和 macOS 安装实例分别计数。

设备记录包括：

- 随机设备 ID。
- 用户自定义名称。
- 平台和体系结构。
- 应用版本。
- 创建时间和最后活动时间。
- 撤销时间和撤销原因。

不采集硬盘序列号、主板序列号、IMEI 或稳定广告 ID。

用户可以在网页和客户端中：

- 查看活跃设备。
- 修改设备名称。
- 撤销丢失或不再使用的设备。
- 查看最近活动时间。

注册第 6 台设备时不封禁账号，提示用户先移除一台旧设备。换机和重装不收费。

## 9. 定价、订单与 Care 权益

### 9.1 产品计划

首发只有一个中国计划：

```text
plan_code: CARE_CN_ANNUAL
currency: CNY
amount_minor: 600
duration_days: 365
```

海外阶段增加：

```text
plan_code: CARE_GLOBAL_ANNUAL
currency: USD
amount_minor: 600
duration_days: 365
```

所有用户使用相同价格，不设计早期价、恢复价或连续续费折扣。

### 9.2 首发支付

首发使用支付宝网页支付。支付适配器隔离支付宝 SDK、签名、回调和订单查询逻辑，会员模块不依赖支付宝特有字段。

同时提供管理后台人工开通能力，用于：

- 付费功能内测。
- 支付渠道尚未开通时验证完整流程。
- 支付异常后的客服处理。
- 合作伙伴和测试账号。

每次人工开通必须记录管理员、原因、开始时间和结束时间。

### 9.3 订单与幂等

- 创建订单必须支持客户端幂等键。
- 支付成功以支付宝服务端验签回调或主动查询结果为准。
- 前端跳转到“支付成功”页面不能直接开通权益。
- 支付宝交易号建立唯一索引。
- 相同回调重复处理只能产生一次权益变更。
- 退款完成后写入引用原始购买事件的负向 `membership_event`，通过固定事件折叠规则更新权益。
- 所有金额使用最小货币单位整数保存。

全额退款规则固定为：退款订单贡献的 365 天从当前投影中扣除，但其他购买和人工赠送的时长保留；扣除后的到期时间不得早于退款确认时间。首发不支持部分退款，同一购买事件只能被冲正一次。

### 9.4 权益周期

- 首次购买从支付成功时开始，有效期 365 天。
- 提前续费从现有到期时间顺延 365 天。
- 已到期后购买从新的支付成功时间开始。
- 到期不影响核心软件和已有配置。
- 到期后停止 Care 安装包下载、迁移和测试版通道，但账号、续费、取消自动续费、查看和撤销现有设备继续可用。
- 用户仍可通过 GitHub 手动更新。

| 能力 | 未登录 | 已登录未购买/已到期 | Care 有效 |

| 查看、改名和撤销现有设备 | 否 | 是 | 是 |

## 10. 自动续费

自动续费是可选功能，不预先勾选。购买页可以将其标为“推荐”，但用户必须主动选择并明确确认代扣协议。

购买页提供两个同价选项：

```text
购买一年        ¥6
每年自动续费    ¥6/年
```

规则如下：

- 用户可以在网页和客户端随时取消。
- 取消后当前年度权益持续到原到期日。
- 每次扣款前至少 5 天发送邮件和客户端提醒。
- 提醒必须写明产品、金额、扣款日期和取消路径。
- 自动续费失败后发送通知并转为手动续费。
- 不在后台连续进行多次不可见扣款。
- 支付渠道未开放周期代扣时，产品自动降级为到期提醒。
- 海外版沿用相同原则。

自动续费可以晚于一次性购买上线，不阻塞 Care 中国付费测试版。

自动续费协议状态固定为：

```text
PENDING -> ACTIVE -> CANCEL_PENDING -> CANCELED
                  `-> PAST_DUE -> EXPIRED
```

用户选择自动续费时，先创建普通首年订单并完成一次性支付；首年 Care 只由支付成功事件开通，不依赖代扣签约结果。支付成功后创建 `PENDING` 续费协议并跳转支付宝签约。只有支付宝服务端签约通知验签成功后才进入 `ACTIVE`；签约未在 30 分钟内完成则进入 `EXPIRED`，首年 Care 仍按手动续费使用。

系统在计划扣款前 5 天发送提醒，到期日只发起一次业务扣款。失败后进入 `PAST_DUE`，不在后台连续重试；24 小时后仍未确认成功则进入 `EXPIRED`，会员在原到期时间结束。用户可以重新购买或重新签约。

取消和扣款按协议记录加数据库锁串行处理：若取消在渠道扣款请求发出前提交，则阻止该次扣款；若渠道已经确认扣款成功，则本次扣款正常增加 365 天，同时协议转为 `CANCELED`，不再发生下一次扣款，用户可以按退款规则申请全额退款。

删除账号时，尚未完成渠道签约的 `PENDING` 协议直接标记为 `CANCELED` 并留下审计记录；`ACTIVE`、`CANCEL_PENDING` 或 `PAST_DUE` 协议必须先向渠道取消。渠道确认或明确不存在协议后才完成账号删除。取消失败时账号进入 `DELETION_PENDING`，撤销所有登录会话并由后台重试，不允许继续发起新扣款。

延迟支付通知按支付事实处理，但绝不能重新激活已终止协议：

- `PAST_DUE` 的成功回调在 24 小时窗口内到达时，正常增加 365 天并恢复协议为 `ACTIVE`。
- 协议已经进入 `EXPIRED` 后才收到成功回调，若账号仍存在且支付发生时间早于取消时间，则把该笔款视为一次性续费，增加 365 天，但协议保持 `EXPIRED`。
- 若账号处于 `DELETION_PENDING`、已经删除，或支付发生时间不晚于用户取消时间，则不增加权益，立即发起全额退款。
- 无法验证支付时间、金额或协议关联时进入 `RECONCILIATION_REQUIRED`，不激活代扣，由后台在 24 小时内人工确认或退款。
- 所有延迟回调继续受交易号唯一约束，不能重复加时或重复退款。

## 11. 数据模型

首发数据库包含以下核心表：

| 表 | 责任 |
|---|---|
| `users` | 用户主体、状态、地区和创建时间 |
| `user_identities` | 邮箱及未来第三方身份 |
| `login_challenges` | 验证码哈希、有效期、尝试次数和消费状态 |
| `devices` | 随机安装 ID、平台、版本和撤销状态 |
| `device_sessions` | 设备刷新令牌哈希和会话状态 |
| `plans` | 地区、价格、币种、周期和可用状态 |
| `orders` | 订单金额、状态、幂等键和用户 |
| `payment_transactions` | 支付渠道交易、验签和退款状态 |
| `payment_events` | 原始回调摘要、处理状态和重复检测 |
| `renewal_agreements` | 自动续费签约、取消和下次扣款信息 |
| `care_memberships` | 当前 Care 周期和状态 |
| `membership_events` | 开通、续费、退款、人工调整的不可变流水 |
| `releases` | 平台、版本、通道、资源和发布状态 |
| `release_compatibilities` | Android、桌面端和协议兼容范围 |
| `update_telemetry` | 仅在用户允许匿名统计时保存的更新结果 |
| `admin_users` | 管理员和双因素认证状态 |
| `audit_events` | 管理操作、安全事件和关键业务变化 |

会员有效期不能只由订单表推导。`membership_events` 保存不可变流水，`care_memberships` 保存当前投影，便于审计和恢复。

### 11.1 会员事件折叠规则

每个 `membership_event` 都有单调递增的 `sequence`、`occurred_at`、`type`、带符号的 `duration_days` 和可选的 `source_order_id`、`reverses_event_id`。

按 `sequence` 顺序折叠：

- `PURCHASE`、`RENEWAL`、`MANUAL_GRANT`：`end = max(end, occurred_at) + duration_days`。
- `REFUND_REVERSAL`：必须引用一个尚未冲正的正向事件；`end = max(occurred_at, end - referenced.duration_days)`。
- `MANUAL_REVOKE`：记录明确的负数天数；`end = max(occurred_at, end + duration_days)`。
- 任何事件都不删除或修改旧事件；`care_memberships.current_period_end` 是折叠后的缓存投影。

测试向量：第 0 天购买 A 得 365 天，第 100 天购买 B 再得 365 天，第 150 天人工赠送 30 天，投影到期日为第 760 天；第 160 天全额退款 B 后扣除 365 天，投影到期日为第 395 天。A 和人工赠送没有被丢弃。

## 12. API 设计

所有动态接口使用 `/api/v1` 前缀。

### 12.1 登录与设备

```text
POST /api/v1/auth/email/challenges
POST /api/v1/auth/email/verify
POST /api/v1/device-authorizations
GET  /api/v1/device-authorizations/{deviceCode}
POST /api/v1/device-authorizations/{userCode}/approve
POST /api/v1/device-authorizations/{userCode}/deny
POST /api/v1/tokens/refresh
POST /api/v1/tokens/revoke
GET  /api/v1/me
GET  /api/v1/me/devices
PATCH /api/v1/me/devices/{deviceId}
DELETE /api/v1/me/devices/{deviceId}
DELETE /api/v1/me
```

### 12.2 订单与权益

```text
GET  /api/v1/plans
POST /api/v1/orders
GET  /api/v1/orders/{orderId}
POST /api/v1/payments/alipay/notifications
GET  /api/v1/me/membership
POST /api/v1/me/renewal-agreements
GET  /api/v1/me/renewal-agreements/current
POST /api/v1/me/renewal-agreements/current/cancel
POST /api/v1/payments/alipay/renewal-notifications
```

### 12.3 更新

```text
POST /api/v1/updates/check
POST /api/v1/updates/{releaseId}/download-tokens
POST /api/v1/updates/{releaseId}/events
```

公开算法更新继续使用当前静态 `/v1/manifest.json` 体系。Care API 不替代已有的公开签名清单，而是在应用包更新前增加账号、设备和权益判断。

`POST /updates/check` 只返回发布元数据、兼容性、发布说明和 `release_id`，不返回下载 URL。用户点击更新时，客户端调用 `POST /updates/{releaseId}/download-tokens`；服务端再次检查设备和 Care 权益，然后创建下载会话，返回有效期 30 分钟的 COS 签名 URL。一个下载会话只能对应一个用户、设备和发布资源，但其 URL 在有效期内允许多个 HTTP Range 请求，以支持暂停、续传和网络重连。这样检查结果缓存不会绕过下载时的权益状态，也不会与断点续传冲突。

### 12.4 自建更新服务器契约

自建更新服务器只替换 Community 的公开算法、模型和手动应用更新源，不代理官方 Care 账号、支付、权益或临时下载授权。

客户端分别保存两个配置：

- `community_update_server_url`：用户可修改，默认官方公开 `/v1` 服务。
- `care_api_base_url`：官方发行版固定为官方 Care API；自行编译者可以在构建时修改。

用户修改 Community 更新源时，必须同时导入该服务器的 Ed25519 根公钥，并在界面确认公钥指纹。客户端不能使用官方公钥信任第三方服务器，也不能因为第三方验签失败自动回退到无签名模式。自建服务器沿用公开 `/v1/manifest.json`、签名、SHA-256、平台和引擎兼容字段，不需要账号认证。

协议选择必须与密钥类型一致：自建 v1 服务器使用用户直接信任的单一 Ed25519 签名公钥；自建 v2 服务器使用用户导入的离线根公钥和根签发的用途密钥证书。官方客户端切换到 v2 后仍允许用户明确选择 v1 自建协议，但不会把 v1 直接信任密钥当作 v2 根证书使用。

官方 Care 权益不自动迁移到自建 Care API。第三方若要提供自己的会员服务，需要自行修改并编译客户端，避免官方账号令牌被发送给未知服务器。

### 12.5 管理后台

管理后台使用浏览器会话和 CSRF 防护，不向客户端公开管理员 API。关键操作需要二次确认并写入审计日志。

## 13. 发布与信任模型

服务端不是安装包信任根。信任关系为：

```text
可信：客户端内置离线根公钥、根签发的用途密钥证书、平台代码签名证书、内置默认算法
不可信：Care API、COS、CDN、网络、访问日志
```

发布流程：

1. CI 构建 Android、Windows 和 macOS 安装包。
2. 在受控发布环境执行平台签名。
3. 生成版本化发布清单和 SHA-256。
4. 使用对应用途的 Ed25519 发布私钥签名清单，并附带离线根密钥签发的用途密钥证书。
5. 上传安装包和签名清单到 COS。
6. 管理后台只登记已经签名的资源。
7. 客户端下载后验证平台签名、清单签名和 SHA-256。
8. 所有验证通过后才进入配置备份和安装步骤。

发布私钥不得保存在 CVM、数据库、COS 或管理后台中。算法更新签名密钥与应用发布签名密钥分开管理。

### 13.1 密钥轮换与恢复

- 客户端只内置长期离线根公钥，不直接长期信任日常发布密钥。
- 算法和应用发布密钥都有 `key_id`、用途、有效期和根签名证书。
- 清单必须由用途匹配且仍在有效期内的密钥签名。
- 正常轮换时，离线根密钥签发下一把用途密钥，客户端无需更新根公钥。
- 用途密钥泄露时，发布根签名的撤销列表和新用途密钥证书；客户端拒绝撤销时间后的旧密钥签名。
- 离线根密钥泄露属于最高等级事件，必须通过平台代码签名渠道和 GitHub 手动发布带新根公钥的客户端；旧更新源暂停发布。
- 离线根私钥保存在断网介质并至少保留两份异地加密备份，日常发布不使用根私钥直接签清单。

根证书、用途密钥证书和撤销文档使用项目自定义的固定 JSON 结构与 Ed25519 签名，不实现通用 X.509 PKI。所有格式都有明确的 `format_version`，未知版本一律拒绝。

### 13.2 现有 `/v1` 客户端迁移

当前客户端只理解直接 Ed25519 签名的 `/v1/manifest.json`，因此不能原地替换为新证书链格式。迁移采用双轨发布：

1. `/v1/manifest.json` 保持现有结构和旧签名方式，继续为已安装客户端提供算法、模型和 profile 更新。
2. 新增 `/v2/manifest.json`，使用离线根公钥、用途密钥证书和撤销文档。
3. 先发布一个同时理解 v1 和 v2 的过渡客户端；该版本仍默认读取 v1，并在后台验证 v2 但不应用。
4. 验证一段发布周期后，新客户端切换到 v2；v2 失败时不能无提示降级为不安全更新，只能继续使用已缓存的最后可信资源。
5. v1 在仍有活跃旧客户端期间继续发布兼容资源，不能改变字段含义或签名算法。
6. v1 旧发布密钥无法安全轮换；若泄露，立即暂停 v1 新发布，并通过 GitHub 和平台签名安装包要求旧客户端升级。

### 13.3 清单新鲜度与防回滚

v2 清单和撤销文档必须包含：

- `format_version`。
- `purpose`。
- `sequence`，在相同根、用途和通道内严格递增。
- `issued_at`。
- `expires_at`。
- `key_id`。

客户端为每个根公钥、用途和通道缓存已接受的最高 `sequence`，拒绝更低序号。清单有效期最长 7 天；撤销文档有独立递增的 `revocation_sequence`，新清单声明最低要求的撤销序号。客户端在接受新安装包或新算法资源前必须取得未过期且序号足够的撤销文档。

网络不可用或撤销文档过期时，客户端可以继续运行已经安装和验证的版本，但暂停接受新更新。Care updater 不接受低于当前已安装发布序号的服务器版本；唯一例外是本地 updater 切换回已经验证并记录为 `known_good` 的上一版本，该操作不依赖服务器清单。

## 14. 更新检查与下载

### 14.1 Community

- 算法配置和模型按现有机制检查并验签。
- 应用安装包通过 GitHub Release 手动获取。
- 用户可以主动点击“检查新版本”并跳转 GitHub。
- 不要求登录或 Care 权益。

### 14.2 Care

1. 客户端每天最多自动检查一次应用更新。
2. 客户端提交平台、架构、应用版本、协议版本和通道。
3. 服务端检查设备和 Care 权益。
4. 服务端返回兼容版本、`release_id`、发布说明和资源大小，不返回下载凭据。
5. 用户点击“一键更新”后，客户端单独创建 30 分钟有效的下载会话，取得支持 HTTP Range 的 COS 签名 URL 并开始下载。
6. 客户端验证签名和哈希。
7. 客户端备份配置并执行平台更新。
8. 新版本启动后执行本地健康检查；只有用户允许匿名统计时才上报更新结果码。

下载会话 URL 有较短有效期，但安装包本身仍必须签名。临时 URL 不是安全边界。

### 14.3 发布选择规则

每个发布都有单调递增的 `release_sequence`、语义版本、平台、架构、通道、状态和兼容范围。服务端先过滤平台、架构、操作系统和协议兼容性，再按以下固定规则选择：

- 稳定通道只考虑 `STABLE + PUBLISHED` 发布。
- 测试通道同时考虑 `STABLE` 和 `BETA`，选择 `release_sequence` 最高的兼容发布。
- `DISABLED`、`DRAFT` 和已过期发布永不返回下载令牌。
- 服务端不向客户端提供低于当前已安装 `release_sequence` 的更新。
- 从测试通道切回稳定通道时，如果当前 beta 序号高于最新 stable，不自动降级；客户端等待后续 stable 追平，或由用户从 GitHub 手动安装。
- 本地 updater 回滚只允许切回本机已验证的 `known_good` 版本，不请求服务器降级包。
- 同一设备上的某发布连续两次健康检查失败后，客户端在本地将该 `release_id` 暂停 7 天；这是设备本地状态，不会全局停用发布。更高 `release_sequence` 发布出现时可以正常尝试。
- 全局停用只能由管理员将发布状态改为 `DISABLED`；已经安装的版本不被远程删除或停用。

测试向量：设备当前稳定序号 40，服务器有 stable 41、beta 42 和 disabled stable 43。稳定通道选择 41；测试通道选择 42；切回稳定时已安装 42 的设备不降级到 41；本地回滚只能回到已记录的 known-good 40。

## 15. 跨端兼容

手机与桌面协议增加明确版本字段：

- `app_version`。
- `protocol_version`。
- `engine_id`。
- `config_schema_version`。

每个发布版本声明：

- 最低兼容桌面端版本。
- 最高已验证桌面端版本。
- 最低兼容 Android 版本。
- 支持的协议范围。
- 支持的配置格式范围。

如果升级顺序有要求，客户端停止安装并给出明确动作，例如：

```text
此 Android 版本需要桌面端 0.4.0 或更高版本。
请先更新电脑端，再更新手机端。
```

兼容检查只阻止应用包安装，不阻止用户继续运行当前版本。

### 15.1 Care v1 支持矩阵

| 平台 | 首发支持 | 安装包 |
|---|---|---|
| Android | Android 6.0 / API 23 及以上，`arm64-v8a`、`armeabi-v7a` | 单一通用 APK |
| Windows | Windows 10 22H2、Windows 11，`x86_64` | 用户级安装包 + 独立 updater |
| macOS | macOS 13 及以上，Apple Silicon `arm64` 和 Intel `x86_64` | 分架构签名、公证 App 包 |

Linux、Windows ARM64 和 ChromeOS 不进入 Care v1。每个发布资源必须声明 `os_min_version`、`architecture` 和 `package_type`，不匹配时更新检查只返回说明，不提供下载令牌。

## 16. 配置备份与迁移

当前 Android SharedPreferences 和桌面 Java Preferences 不适合直接做跨版本备份。需要增加统一的版本化配置导出模型：

```json
{
  "schema_version": 1,
  "created_at": "2026-07-11T00:00:00Z",
  "platform": "android",
  "settings": {}
}
```

设计要求：

- 每个平台提供当前配置到版本化 JSON 的适配器。
- JSON 只包含用户可迁移设置，不包含访问令牌和密钥。
- 每次安装前生成本地快照。
- 迁移器必须逐版本执行，不能跳过未知格式。
- Windows 和 macOS 新版本读取失败时由旧版本恢复对应旧快照。
- Android 新版本必须兼容读取最近两个旧配置版本，迁移写入临时文件并在完整验证后原子替换。
- 快照默认只保留最近 3 份。
- 配置默认不上传云端。

## 17. 平台升级方式

### 17.1 Android

- 下载并验证 APK。
- 校验包名、签名证书和 `versionCode`。
- 调起 Android 系统安装界面。
- 用户必须明确确认安装。
- 系统安装失败时旧 APK 仍然存在。
- APK 替换成功后，新版本在迁移失败时进入“安全配置模式”：保留旧快照，加载内置默认配置，允许用户重试迁移或导出旧快照；不能把新版本无法读取的旧格式直接覆盖回当前配置。
- 不承诺静默安装和自动二进制降级。

### 17.2 Windows

- 独立 updater 进程运行，避免主程序替换自身文件。
- 默认安装到用户目录，减少管理员权限要求。
- 每个应用版本使用独立目录。
- 启动器指向当前有效版本。
- 更新前关闭主程序并备份配置。
- updater 使用 `--post-update <updateId>` 启动新版本，并等待最多 30 秒的本地健康标记。
- 健康检查要求进程可启动、核心类库完成初始化、配置格式成功载入且本地控制服务可创建；不要求摄像头权限、设备连接或互联网可用。
- 30 秒内没有健康标记、进程异常退出或配置载入失败时，启动器切回旧版本和旧配置。
- 保留当前和上一个稳定版本。

### 17.3 macOS

- 使用签名并公证的 App Bundle。
- updater 在主程序退出后替换 App。
- 更新前验证 Team ID、包标识、签名和清单哈希。
- updater 使用与 Windows 相同的 30 秒本地健康标记；失败时恢复旧 App 和旧配置。
- 发布前需要准备 Apple Developer ID 和公证流程。

Windows 和 macOS 连续两次更新启动失败后，在当前设备上暂停该版本 7 天并继续运行旧版本；用户可以手动重试，出现更高 `release_sequence` 的兼容版本时也可以立即尝试，无需等待 7 天结束。

Windows 和 macOS 平台签名证书属于 Care 上线前置条件，不应等到功能完成后才申请。

## 18. 隐私与数据边界

### 18.1 Care 必需数据

提供会员服务所必需的数据包括：

- 邮箱。
- 订单和支付状态。
- Care 有效期。
- 设备名称、平台和版本。
- 下载授权请求、登录和支付所必需的安全日志。

### 18.2 可选匿名统计

匿名统计与会员数据分开处理。可选数据可能包括：

- 应用版本和平台。
- 大致使用时长。
- 更新成功或失败类别。
- 匿名崩溃类型。

不得收集：

- 摄像头画面。
- 音频。
- 人脸或嘴部 landmark。
- 按键内容。
- 游戏或语音软件名称。
- 完整 IP 长期历史。

用户关闭匿名统计后，不再调用 `/updates/{releaseId}/events`，也不发送可选使用数据。下载授权和支付审计仍按提供 Care 服务所必需的数据保存，但不包含门控使用情况。关闭统计不影响 Community 或 Care 权益。

## 19. 安全设计

- API 全部使用 HTTPS。
- 邮箱验证码和刷新令牌只保存哈希。
- 访问令牌短期有效。
- 刷新令牌按设备撤销和轮换。
- 管理后台启用 TOTP 双因素认证。
- 支付回调强制验签、金额校验和商户号校验。
- 订单和支付事件使用数据库唯一约束保证幂等。
- 用户端和管理端分别配置限流。
- 登录、支付、下载和管理操作保留安全审计。
- 密钥通过环境或密钥服务注入，不写入仓库和镜像。
- 数据库每日加密备份，并定期执行恢复演练。
- 服务端依赖和容器镜像定期扫描。
- 更新清单签名失败时客户端必须回退到内置默认和旧版本。

## 20. 故障处理

| 故障 | 行为 |
|---|---|
| Care API 无法访问 | 核心门控继续工作，登录、支付和更新稍后重试 |
| 邮件发送失败 | 不创建可用验证码，显示稍后重试，不锁定核心功能 |
| 支付页面返回成功但无回调 | 主动查询支付宝订单，确认后再开通 |
| 支付回调重复 | 唯一约束和幂等事务阻止重复加时 |
| 自动续费失败 | 通知用户，转为手动续费，不连续隐藏重试 |
| 第 6 台设备注册 | 提示移除旧设备，不封禁账号 |
| 下载中断 | 支持续传或重新下载，旧版本继续运行 |
| 安装包验签失败 | 删除临时文件并记录安全事件 |
| Windows/macOS 配置迁移失败 | 回到旧版本并恢复对应旧快照 |
| Windows/macOS 健康检查失败 | 切回上一版本 |
| Android APK 安装失败 | 系统保留旧 APK 和原配置 |
| Android 新版本配置迁移失败 | 保留旧快照并进入安全配置模式，使用内置默认配置 |
| 更新服务器被攻破 | 客户端因签名不匹配拒绝安装 |

## 21. 管理后台

首发后台只包含必要运营能力：

- 用户和邮箱身份查询。
- Care 状态和历史事件查询。
- 设备列表和撤销。
- 订单、支付交易和退款状态查询。
- 人工开通、延长和撤销 Care。
- 版本、通道和兼容关系管理。
- 发布资源登记和停用。
- 邮件发送和更新失败概览。
- 管理员审计日志。

后台不能上传未签名资源并直接发布。它只能引用通过离线发布工具生成的签名清单和资源。

## 22. 通知

首发使用邮件和客户端内通知，不使用短信。

通知场景：

- 邮箱验证码。
- 手动续费到期前 30 天、7 天和当天。
- 自动续费扣款前至少 5 天。
- 自动续费成功或失败。
- Care 开通、取消和退款。
- 重要安全事件，例如新设备授权或设备撤销。

营销邮件必须与服务通知分开。用户拒绝营销邮件后仍可收到账号、支付和安全所必需的事务邮件。

## 23. 部署与运维

开发和生产环境分开：

```text
Development / staging
  Tencent Cloud Tokyo CVM
  synthetic or explicitly approved test data only

China production
  Tencent Cloud mainland region
  Caddy
  Care API
  PostgreSQL
  encrypted backup job

Tencent COS / CDN
  installers
  manifests
  models
  profiles
```

中国正式收费前，账号、订单、设备和日志的生产数据库部署到腾讯云中国大陆区域，并完成域名、备案、隐私政策和支付主体所需准备。东京服务器可以继续托管公开静态更新镜像，但不得作为中国 Care 个人信息数据库的默认生产位置。

初期可以在同一中国大陆 CVM 运行 API 和 PostgreSQL，但数据库不开放公网端口。增长后优先迁移到独立托管数据库，而不是拆业务微服务。

运维要求：

- 只开放 `80/443`，SSH 仅允许固定 IP 或 VPN。
- 禁止 SSH 密码登录和 root 远程登录。
- 应用以非特权用户运行。
- 数据库每日备份，至少保留 14 天。
- 每月执行一次恢复抽检。
- 监控证书到期、API 错误率、邮件失败率、支付回调积压和备份状态。
- 日志脱敏并设置保存期限。
- 私钥、支付宝密钥和数据库凭据定期轮换。

### 23.1 数据保留与删除

| 数据 | 保留规则 |
|---|---|
| 未使用或已消费邮箱验证码 | 24 小时内删除 |
| 活跃用户和邮箱身份 | 账号存在期间保留；删除账号后 24 小时内删除 |
| 活跃设备 | 设备存在期间保留；撤销或删除账号后保留最小审计字段 180 天再删除 |
| 活跃设备会话 | 到期或撤销后 30 天删除 |
| HTTP 访问日志 | 30 天 |
| 安全审计日志 | 180 天 |
| 管理员财务和权益操作审计 | 3 年 |
| 可选匿名统计原始记录 | 90 天后删除或聚合 |
| 订单、支付和退款记录 | 至少 3 年，满足财务或监管要求时延长 |
| Care 会员和权益事件 | 3 年；账号删除后解除与可登录身份的直接关联 |
| 自动续费协议 | 终止后 3 年，保存渠道协议号、状态和审计字段 |
| 事务邮件发送历史 | 180 天，仅保存模板、状态和脱敏收件人摘要 |
| 发布、兼容和签名元数据 | 长期保留，供旧客户端和安全审计使用 |
| 数据库备份 | 14 天滚动保留 |

用户中心提供“删除账号”。确认后立即撤销会话和设备，并在 24 小时内删除邮箱身份和非必要个人资料；订单、支付和退款记录按法定保留需要保存，但与可登录身份解除关联并限制访问。删除动作会在 14 天内随滚动备份自然清除。匿名聚合统计不反向恢复用户身份。

中国付费发布前必须完成一次数据清单和隐私影响检查；若中国大陆生产环境、备案或隐私文件未准备完成，只能进行使用合成数据的内测，不能开放真实付费用户。

## 24. 测试策略

### 24.1 单元测试

- 验证码状态机和限流。
- `device_code` / `user_code` 分离、轮询状态和一次性领取。
- 设备数量限制和撤销。
- Care 首购、提前续费、到期后购买和退款。
- 退款后基于未退款事件重新计算权益。
- 自动续费取消、成功和失败。
- 删除账号时取消 `PENDING`、`ACTIVE` 和 `PAST_DUE` 协议。
- 延迟支付成功回调、取消竞态和 `RECONCILIATION_REQUIRED`。
- 订单、回调和权益幂等。
- 未登录、已到期和 Care 有效状态的接口访问矩阵。
- 版本选择和兼容矩阵。
- 配置迁移和回滚。

### 24.2 集成测试

- PostgreSQL + Flyway 全量迁移。
- 支付宝沙箱支付和回调验签。
- 腾讯云 SES 测试账号和失败注入。
- COS 临时 URL 和下载授权。
- Ed25519 清单签名和篡改拒绝。
- 根签发用途密钥、正常轮换和撤销列表。
- 自建 Community 更新源、公钥指纹确认和 Care API 隔离。
- 设备授权浏览器流程。

### 24.3 端到端测试

- 新用户邮箱登录、付款、开通 Care 和绑定设备。
- `PENDING` 签约期间删除账号、渠道取消失败和延迟扣款退款。
- 第 5 台设备成功、第 6 台设备被友好阻止。
- Android、Windows、macOS 更新成功路径。
- 网络中断、下载损坏、迁移失败和回滚路径。
- Windows/macOS 30 秒健康检查成功、超时和异常退出。
- Android 迁移失败后进入安全配置模式。
- Care 到期后核心功能继续使用。
- Care 到期后仍可登录、续费、取消续费和撤销设备。
- 关闭匿名统计后不发送更新事件。
- Community 用户无需账号完成安装和使用。

### 24.4 发布验证

- Android 真机。
- Windows 10 22H2、Windows 11 `x86_64` 虚拟机和真机。
- macOS 13 及以上的 Apple Silicon 和 Intel 可用性验证。
- Android API 23 及以上的 `arm64-v8a` 和 `armeabi-v7a` 真机或模拟器覆盖。
- 从最近两个稳定版本升级到最新版本。
- 数据库从空库和上一生产版本迁移。
- 备份恢复演练。

## 25. 分阶段路线

### 阶段 0：发行基础，1–2 周

- 统一应用、协议和配置版本字段。
- 定义跨端兼容清单。
- 建立离线签名与发布流程。
- 启动平台代码签名证书准备。

### 阶段 1：会员后端，2–3 周

- Spring Boot 模块化单体。
- PostgreSQL 和 Flyway。
- 邮箱验证码登录。
- 浏览器设备授权。
- 5 台设备管理。
- 最小管理后台和人工开通。

### 阶段 2：支付权益，1–2 周

- 支付宝一次性支付。
- 订单、支付回调和主动查询。
- Care 权益流水和到期逻辑。
- 退款与人工调整。
- 真实支付测试前部署中国大陆生产环境，发布隐私政策、服务协议和账号删除入口；未完成前只使用支付宝沙箱和合成账号。

### 阶段 3：客户端会员，2–3 周

- Android、Windows、macOS Care 登录。
- 系统安全存储。
- 会员和设备页面。
- 更新通道和兼容提示。

### 阶段 4：三端升级器，4–6 周

- Android APK 验签与系统安装。
- Windows 独立 updater 和版本目录回滚。
- macOS 签名、公证和 App 回滚。
- 版本化配置、迁移和快照。

### 阶段 5：自动续费，1–2 周

- 用户主动签约。
- 扣款前提醒。
- 随时取消。
- 成功、失败和到期处理。

### 阶段 6：正式运营，1–2 周

- 监控、备份、告警和恢复演练。
- 隐私政策、服务协议和自动续费协议。
- 公开更新接口和签名机制文档。
- 中国正式版发布检查。

总工程量估算为单人持续开发 `12–18 周`。该估算用于排期和范围管理，不是硬性交付承诺。

### 25.1 实施计划拆分边界

本规格描述完整平台，但不生成一个覆盖全部系统的超大实施计划。后续依次编写并执行以下独立计划：

1. 发布信任、版本协议和自建 Community 更新源。
2. 账号、设备和最小管理后台。
3. 支付、会员权益和通知。
4. 三端会员登录与客户端页面。
5. 版本化配置与迁移框架。
6. Android updater。
7. Windows updater。
8. macOS updater。
9. 自动续费。
10. 中国生产部署、隐私和运营准备。

每个计划必须产生可独立验证的软件或运营能力，并通过对应验收后再开始下一项。

## 27. 验收标准

Care 正式版必须同时满足：

1. 未登录用户可完整使用 Community 核心功能。
2. Care API 完全离线时，已安装客户端仍能识别和控制按键。
3. 邮箱登录不使用密码和短信。
4. 支付重复回调不会重复增加权益。
5. 每个账号最多 5 台设备，用户可自行解绑。
6. 自动续费不默认勾选，并能在网页和客户端取消。
7. 扣款前完成显著提醒。
8. 所有应用更新包在安装前完成签名和哈希验证。
9. Windows 和 macOS 更新在 30 秒健康检查失败后可以切回上一版本。
10. Android APK 安装失败不会破坏现有安装；新版本配置迁移失败会进入安全配置模式并保留旧快照。
11. 跨端不兼容版本不会被直接安装。
12. Windows/macOS 配置迁移失败会随二进制回滚恢复旧快照；Android 会保留旧快照并进入安全配置模式，不把不可读旧格式直接覆盖为当前配置。
13. Community 用户可以从 GitHub 手动更新。
14. 关闭匿名统计不会影响任何付费权益。
15. 服务端不接收音频、视频或人脸、嘴部识别数据。
16. 自建 Community 更新源不能接收官方 Care 账号令牌，也不能绕过签名验证。
17. 中国付费版的账号和支付数据不以东京 CVM 作为默认生产数据库。
18. 删除账号后按数据保留矩阵撤销、删除或解除关联数据。

## 28. 风险与应对

| 风险 | 应对 |
|---|---|
| `¥6/年` 单用户收入很低 | 保持单体架构、邮件登录和低运维复杂度 |
| 支付或自动续费资质延期 | 人工开通和一次性支付先上线，自动续费后置 |
| Windows/macOS 更新器工程量大 | 分平台独立验收，不承诺统一实现细节 |
| macOS/Windows 签名证书准备慢 | 阶段 0 立即启动申请和验证 |
| 服务器被攻破 | 客户端离线公钥验签，私钥不在服务器 |
| 开源代码可以绕过客户端 Care 判断 | 服务端验证官方下载权益；不把防破解作为商业核心 |
| 中国生产环境和备案准备耗时 | 东京只做开发和静态镜像；付费上线前完成中国大陆部署和合规检查 |
| 邮箱验证码被滥用 | 多维限流、人机验证和发送配额告警 |
| 设备误判导致客服成本 | 使用软限制和用户自助解绑，不使用硬件指纹 |
| 自动续费投诉 | 用户主动选择、显著提醒、简单取消和完整审计 |
